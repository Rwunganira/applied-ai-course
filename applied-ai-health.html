Weeks 1–3

Data foundations

All AI rests on clean data. You already work with line lists. Here you'll make that data reliable, reproducible and ready for models.

WEEK 01

From line list to weekly counts

pandas for surveillance data›

The idea

A line list has one row per case. Almost every model in this course needs something different: one row per district per week, with a count. Turning the first into the second, correctly, is the most useful data skill in public health AI.

Think of it like this: the line list is the register at the health centre. Weekly counts are the tally sheet you send to the district. The model only ever sees the tally sheet.

Simple example

# one row per case  →  one row per district per week
import pandas as pd

cases = pd.read_csv("line_list.csv", parse_dates=["onset_date"])

weekly = (cases
    .groupby(["district", pd.Grouper(key="onset_date", freq="W-MON")])
    .size()
    .rename("cases")
    .reset_index())

# the trap: weeks with zero cases are missing, not 0
full = (weekly.set_index(["district", "onset_date"])
    .unstack(fill_value=0).stack()
    .reset_index())

WEEK 02

SQL, APIs and DHIS2

Getting data out of the systems where it lives›

The idea

Real surveillance data lives in databases and in DHIS2, not in CSV files. SQL lets you ask a database a question. An API lets your code ask another system (like DHIS2) for data automatically, so nobody has to export spreadsheets by hand.

Think of it like this: SQL is asking the records clerk a precise question. An API is a standing arrangement where the clerk sends the answer to your office every Monday, without being asked.

Simple example

-- the week-1 aggregation, done by the database instead
SELECT district,
       date_trunc('week', onset_date) AS week,
       COUNT(*)                       AS cases
FROM   cases
GROUP  BY district, week
ORDER  BY district, week;

WEEK 03

How machine learning actually thinks

Training, testing, overfitting, baselines›

The idea

A machine-learning model learns patterns from past examples, and you judge it only on examples it has never seen. There are three rules. Hold data back for testing. With time data, never let the model see the future. And always compare against a simple baseline. A model that can't beat “next week will be the same as this week” is not worth having.

Think of it like this: a student who memorises last year's exam answers scores 100% on last year's exam and fails this year's. That is overfitting. The test set is this year's exam.

Simple example: the baseline every model must beat

# "naive" forecast: next week = this week
df = full.sort_values(["district", "onset_date"])
df["prediction"] = df.groupby("district")["cases"].shift(1)

mae = (df["cases"] - df["prediction"]).abs().mean()
print(f"Baseline is off by {mae:.1f} cases per week on average")

WEEK 04

Classification: is this suspected case likely confirmed?

Logistic regression, gradient boosting, the 2×2 table›

The idea

A classifier sorts things into groups, such as “likely lab-confirmed” or “likely not”. You already know how to judge one: the confusion matrix is the 2×2 table you use to evaluate a diagnostic test.

You already know this table

Lab positiveLab negative
Model says positive42  TP15  FP
Model says negative8  FN135  TN

Example numbers. Sensitivity = 42 / 50 = 84%. Specificity = 135 / 150 = 90%. In machine learning, sensitivity is called recall.

Simple example

from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import confusion_matrix

X = df[["fever", "rash", "cough", "age_years", "vaccinated"]]
y = df["lab_confirmed"]
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.25, stratify=y, random_state=1)

model = LogisticRegression(max_iter=1000).fit(X_train, y_train)
tn, fp, fn, tp = confusion_matrix(y_test, model.predict(X_test)).ravel()
print("sensitivity", tp / (tp + fn), "specificity", tn / (tn + fp))

WEEK 05

Forecasting next month's cases

Time series, lag features, seasonality›

The idea

To forecast, turn the past into columns. “Cases 1 week ago”, “2 weeks ago” and “52 weeks ago” become features, and the model learns how they relate to this week. Seasonal diseases like malaria and influenza reward the 52-week lag.

Think of it like this: a district officer who says “it's March, rains just started, and cases rose the last two weeks, so expect more” is doing lag-feature forecasting in their head.

Simple example

from sklearn.ensemble import HistGradientBoostingRegressor

for lag in [1, 2, 3, 52]:
    df[f"lag_{lag}"] = df.groupby("district")["cases"].shift(lag)

features = ["lag_1", "lag_2", "lag_3", "lag_52"]
train = df[df["onset_date"] <  "2025-01-01"]
test  = df[df["onset_date"] >= "2025-01-01"]   # never shuffle time data

model = HistGradientBoostingRegressor().fit(train[features], train["cases"])
test_mae = (test["cases"] - model.predict(test[features])).abs().mean()
# compare with your week-3 baseline: did it actually help?

This week

WEEK 06

Outbreak signals: anomaly detection

EARS-style thresholds, false alarms, Farrington›

The idea

Anomaly detection asks: is this week unusually high compared with what's normal here? The classic surveillance method, EARS C2, compares today with the average of recent days, leaving a short gap in between so a rising outbreak doesn't hide itself in its own baseline.

Think of it like this: a smoke alarm. Set it too sensitive and it goes off every time you cook, so people stop listening. Set it too loose and it misses the fire. You tune it by counting false alarms.

Simple example (EARS C2 on daily counts)

g = daily.groupby("district")["cases"]
# baseline = days t-3 … t-9 (7 days, 2-day guard band)
mean = g.transform(lambda s: s.shift(3).rolling(7).mean())
sd   = g.transform(lambda s: s.shift(3).rolling(7).std())

daily["alert"] = daily["cases"] > mean + 3 * sd

WEEK 07

LLM basics and structured extraction

Tokens, context, prompts, JSON output›

The idea

A large language model reads text and predicts a continuation. It is excellent at language and can be confidently wrong about facts. The most dependable first use is extraction: turning messy free text into clean fields your code can check.

Think of it like this: a very fast data clerk who has read everything but has never visited your district. Give it exact instructions and a form to fill in, then check its work.

Simple example: free-text note → case record

from pydantic import BaseModel
import anthropic

class CaseReport(BaseModel):
    age_years: int | None
    sex: str | None
    symptoms: list[str]
    onset_date: str | None
    suspected_disease: str | None

client = anthropic.Anthropic()
note = "Pt 34F, fever and bloody diarrhoea since 12 Sept, 3 household contacts ill."

response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=1024,
    messages=[{"role": "user",
               "content": f"Extract the case details from this clinical note:\n{note}"}],
    output_format=CaseReport,
)
print(response.parsed_output)   # a validated CaseReport, not loose text

Use simulated or de-identified notes only. Week 11 covers why.

WEEK 08

RAG: answering from your own documents

Chunking, retrieval, grounded answers with sources›

The idea

RAG (retrieval-augmented generation) answers a question in three steps. Find the passages in your documents most related to the question. Give only those passages to the model. Tell it to answer from them and cite them. This is how you make an AI answer from WHO case definitions instead of from memory.

Think of it like this: a closed-book exam versus an open-book exam. RAG turns every question into an open-book exam, and a good answer points to the page.

Simple example: retrieval with no extra services

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

chunks = load_paragraphs("guidelines/")   # your own helper: one paragraph per item
vec = TfidfVectorizer().fit(chunks)
doc_matrix = vec.transform(chunks)

def retrieve(question, k=3):
    scores = cosine_similarity(vec.transform([question]), doc_matrix)[0]
    return [chunks[i] for i in scores.argsort()[::-1][:k]]

question = "What is the suspected case definition for cholera?"
context = "\n\n".join(retrieve(question))
prompt = (f"Answer using only these excerpts. If the answer is not in them, "
          f"say so.\n\n{context}\n\nQuestion: {question}")
# then send `prompt` with client.messages.create(...) as in week 7

WEEK 09

Tools and agents

Letting the model ask your code for data›

The idea

The model can't query your database, but it can ask your code to. You describe a tool (its name, what it does and what inputs it takes). The model replies “please call get_weekly_cases for district X”. Your code runs it and sends back the result, and the model writes the answer. An agent is this loop repeated until the task is done.

Think of it like this: a manager who can't access the database but knows exactly which report to request from the data officer, reads it, then asks for the next one.

Simple example: describing a tool

tools = [{
    "name": "get_weekly_cases",
    "description": "Weekly case counts from EpiTracker for one district and disease.",
    "input_schema": {
        "type": "object",
        "properties": {
            "district": {"type": "string"},
            "disease":  {"type": "string"},
            "weeks":    {"type": "integer", "description": "How many recent weeks"},
        },
        "required": ["district", "disease"],
    },
}]

# the loop: ask → model requests a tool → you run it → send the result → repeat
messages = [{"role": "user", "content": "Is cholera rising in District A?"}]
while True:
    response = client.messages.create(model="claude-opus-5", max_tokens=16000,
                                      tools=tools, messages=messages)
    if response.stop_reason != "tool_use":
        break
    messages.append({"role": "assistant", "content": response.content})
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": str(run_tool(b.name, b.input))}
               for b in response.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})

WEEK 10

Evaluation: M&E for AI

Gold sets, indicators, regression testing›

The idea

This is the week where your background is rarest in the job market. Evaluating an AI system is monitoring and evaluation. You define indicators, build a reference dataset with known answers (a “gold set”), measure against it, and re-measure after every change. Most people who build AI tools skip this step.

Think of it like this: a logframe for your assistant. The indicator is “% of guideline questions answered correctly with a valid source”. The means of verification is a 40-question gold set. The target is 90%.

Simple example

gold = [
    {"q": "Suspected cholera case definition?", "must_contain": "acute watery diarrhoea"},
    {"q": "What is the incubation period of measles?", "must_contain": "10"},
    {"q": "Dose of drug X for adults?", "must_contain": "not in the documents"},  # should refuse
    # … 40 questions in total
]
correct = sum(g["must_contain"].lower() in ask(g["q"]).lower() for g in gold)
print(f"Accuracy: {correct / len(gold):.0%}")

This week

Exercise

Build

WEEK 11

Bias, privacy and human oversight

Subgroup performance, de-identification, model cards›

The idea

A model can look accurate overall and still fail one group. A classifier trained mostly on urban hospital data may miss cases in rural clinics. Always measure performance by subgroup. Health data is also sensitive: de-identify it before it leaves your system, respect your national data protection law and data-sharing agreements, and keep a person responsible for every decision.

Think of it like this: you would never report national vaccination coverage without breaking it down by district. Hold models to the same standard.

Simple example: sensitivity by subgroup

test["pred"] = model.predict(X_test)
positives = test[test["lab_confirmed"] == 1]
print(positives.groupby("facility_type")["pred"].mean())   # sensitivity per group
# urban 0.88, rural 0.61  →  that gap is the finding

Exercise

WEEK 12

Capstone and portfolio

Make the work visible›

The idea

Employers hire from what they can see. Your capstone is EpiTracker as it stands now, with counts, forecasts, alerts, a guidelines assistant and an evaluation scorecard, presented so a hiring manager understands it in five minutes.

What to deliver

  • A public GitHub repository with a README that has a screenshot and a “what problem this solves” section in its first 10 lines
  • A 3-minute screen-recorded demo
  • A 1,000-word case study covering the problem, approach, evaluation results, limits and what you'd do next
  • Your week-11 model card
  • A LinkedIn post that links to all of the above

Self-assessment rubric

  • Works: someone else can run it by following your README
  • Measured: every model and assistant reports a number against a baseline or gold set
  • Honest: limits and subgroup gaps are stated, not hidden
  • Useful: a district surveillance officer would want to open it on Monday morning
Delivery

The best way to take this course

Self-paced and project-based, with one project running through every week. Short courses that jump between unrelated toy datasets rarely stick, because nothing builds on anything. One project that grows each week gives you a reason to learn every topic and a portfolio at the end.

For you, learning alone

  1. Protect the time. Put two fixed blocks in your calendar every week, for example two weekday evenings and Saturday morning.
  2. Use Claude as a tutor, not a ghostwriter. Write your own attempt first, then ask for a review. Ask it to quiz you, or explain the concept back to it until it finds no gaps.
  3. Type the examples, don't paste them. Your fingers learn what your eyes skim past.
  4. Keep a public build log. Five lines a week on GitHub or LinkedIn. By week 12 it proves you stayed consistent.
  5. Hold checkpoints in weeks 3, 6, 10 and 12. If you're behind, cut the Build step, never the Exercise.

If you later teach it to others

You already build course platforms, so this could become a course you run through mecourse:

  • A cohort of 10–25 people starting together, so peers keep each other going
  • Blended format: reading and short videos on your platform, plus a 90-minute live lab each week
  • Ready-to-run notebooks (Google Colab) so nobody gets stuck installing software
  • Projects instead of quizzes: assess the weekly builds and the capstone with the rubric above
  • Peer review of each other's evaluation scorecards in week 10
